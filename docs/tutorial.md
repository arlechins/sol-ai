# Tutorial: from clone to a live reputation loop

This walkthrough takes a clean machine to a running local deployment, then to
the TypeScript SDK, the MCP server, and finally a devnet deployment. Every
command is copy-pasteable and matches the scripts in this repository.

Program under test: `taop_reputation`
(`8soD4YteLDgkibSNBzmQJTztiNcXPcLoi3Y2FrY15MnE`, Anchor `1.1.2`).

## 1. Prerequisites

### Rust (stable)

```sh
rustup toolchain install stable
rustup default stable
rustc --version
```

### Solana CLI 4.2.x (Agave)

```sh
sh -c "$(curl -sSfL https://release.anza.xyz/stable/install)"
export PATH="$HOME/.local/share/solana/install/active_release/bin:$PATH"
solana --version    # 4.2.x
```

The repository scripts and CI are pinned to Solana `4.2.2`; any 4.2.x release
works. Keep the install directory on `PATH` for the rest of this tutorial
(`scripts/localnet.sh` adds the same path itself).

### Anchor CLI 1.1.2

Anchor 1.1.2 ships prebuilt binaries on the otter-sec fork used by this repo:

<https://github.com/otter-sec/anchor/releases>

```sh
mkdir -p "$HOME/.local/bin"
curl -sSfL -o "$HOME/.local/bin/anchor" \
  "https://github.com/otter-sec/anchor/releases/download/v1.1.2/anchor-1.1.2-x86_64-unknown-linux-gnu"
chmod +x "$HOME/.local/bin/anchor"
export PATH="$HOME/.local/bin:$PATH"
anchor --version     # anchor-cli 1.1.2
```

On macOS pick the asset matching your CPU (`aarch64-apple-darwin` for Apple
silicon, `x86_64-apple-darwin` for Intel) from the same release page.

`Anchor.toml` pins `anchor_version = "1.1.2"`, so do not use a newer or older
CLI — the generated IDL and `declare_program!` in the Rust tests must match.

### Node 20+ and pnpm 9

```sh
node --version      # v20 or newer
corepack enable
corepack prepare pnpm@9.15.4 --activate
pnpm --version      # 9.15.4
```

The workspace's root `package.json` declares `"packageManager": "pnpm@9.15.4"`
and `"node": ">=20"`.

## 2. Install, build, and test

```sh
git clone https://github.com/arlechins/sol-ai.git
cd sol-ai

pnpm install
anchor build
./scripts/sync-idl.sh
cargo test --workspace
```

- `anchor build` produces `target/deploy/taop_reputation.so`, the IDL at
  `target/idl/taop_reputation.json`, and TypeScript types at
  `target/types/taop_reputation.ts`.
- `./scripts/sync-idl.sh` copies the IDL into
  `idls/` (used by `declare_program!` in the Rust
  tests) and the IDL + types into `packages/solana/src/idl/` for the SDK.
  `cargo test` fails to compile without this step.
- `cargo test --workspace` runs **71 tests**: 60 LiteSVM integration tests
  (`test-suite/tests/config.rs`, `test-suite/tests/reputation.rs`,
  `test-suite/tests/capability.rs`, `test-suite/tests/invariants.rs`,
  `test-suite/tests/security.rs`, `test-suite/tests/hardening.rs`), 10 score
  unit tests in `src/state.rs` (5 example-based and 5 property-based), and 1
  `test_id` test generated by the `declare_program!` macro. The suite loads the
  built `.so` from `target/deploy/`, so `anchor build` must run first.

Run the SDK tests:

```sh
pnpm --filter @taopp/solana test
```

This runs 12 Vitest tests: 6 unit tests for `computeScore`, `hashType`, and PDA
derivation (no chain required) and 6 end-to-end tests that exercise the SDK
against a live validator. The integration suite is skipped automatically when
the RPC endpoint is unreachable, so use the next section to get all 12.

## 3. Local end-to-end (localnet)

### 3.1 Start the validator and deploy

```sh
./scripts/localnet.sh
```

The script:

- creates `~/.config/solana/id.json` if it does not exist,
- starts `solana-test-validator` on `http://127.0.0.1:8899` with
  `--clone-feature-set --url https://api.devnet.solana.com` (needed so the
  validator advertises the same SBPF feature set the program was built for),
- airdrops 500 SOL to the wallet,
- deploys `target/deploy/taop_reputation.so` using the program keypair at
  `target/deploy/taop_reputation-keypair.json`.

It leaves the validator running and prints the RPC URL. Re-running it detects
the running validator and only re-deploys. Set `ANCHOR_WALLET` to use a
different wallet file.

### 3.2 Run the example agent

The example runs two independent agents and a certifier through the full trust
loop:

```sh
CERTIFIER_KEYPAIR=~/.config/solana/id.json \
  pnpm --filter @taopp/example-solana-agent start -- --cluster localnet
```

On devnet, pass funded keypair files with absolute paths (the command runs from
the package directory) and reclaim the demo capability bond afterwards:

```sh
AGENT_A_KEYPAIR="$PWD/.keys/agent-a.json" \
AGENT_B_KEYPAIR="$PWD/.keys/agent-b.json" \
CERTIFIER_KEYPAIR=~/.config/solana/id.json \
  pnpm --filter @taopp/example-solana-agent start -- --cluster devnet

AGENT_A_KEYPAIR="$PWD/.keys/agent-a.json" \
  pnpm --filter @taopp/example-solana-agent start -- --cluster devnet --reclaim
```

`--reclaim` withdraws every active capability bond owned by `AGENT_A_KEYPAIR`,
so demo runs do not strand SOL. The challenge bond is refunded automatically
when the certifier upholds the challenge.

Expected shape of the output:

```text
TAOP Solana example agent — cluster=localnet rpc=http://127.0.0.1:8899
mode=sdk

== Agent A: register profile and bond a capability
capability: <pubkey>
https://explorer.solana.com/address/<pubkey>?cluster=localnet
capability certified by the certifier

== Agent A: complete a task and self-attest
completion #1: <pubkey>
https://explorer.solana.com/tx/<signature>?cluster=localnet

== Agent B: discover capabilities and vet Agent A
chose <agent-a-pubkey> score=1 bond=5000000 certified=true
Agent A score before challenge: 1

== Agent B: challenge the completion with a native SOL bond
https://explorer.solana.com/tx/<signature>?cluster=localnet

== Certifier: resolve the challenge as upheld
https://explorer.solana.com/tx/<signature>?cluster=localnet

== Agent B: re-read Agent A's score
score: 1 -> 0 (disputes: 1)

The loop is complete: discovery, bonded challenge, resolution, and a decayed score — all on-chain.
```

If `CERTIFIER_KEYPAIR` is not set, the capability stays uncertified and the
challenge stays pending; the script prints instructions for both cases.

Agent keypairs are read from `AGENT_A_KEYPAIR` / `AGENT_B_KEYPAIR` (a file path
or a base58 secret). When unset, the example generates ephemeral keypairs and
airdrop 1 SOL each on localnet/devnet. See
`examples/solana-agent/README.md` for details.

### 3.3 Run the SDK integration tests

With the validator from `./scripts/localnet.sh` still running:

```sh
pnpm --filter @taopp/solana test
```

The integration suite initializes the config if needed, registers and attests
as an agent, reads the score both locally and through the on-chain `get_score`
instruction, challenges and resolves a completion, then registers, certifies,
discovers, slashes, and withdraws a capability. Point it at another cluster
with `TAOP_RPC_URL`.

## 4. SDK walkthrough

Install the package:

```sh
pnpm add @taopp/solana
```

### 4.1 Connect (read-only)

```ts
import { Connection, PublicKey } from "@solana/web3.js";
import { TaopSolanaClient } from "@taopp/solana";

const connection = new Connection("http://127.0.0.1:8899", "confirmed");
const client = new TaopSolanaClient({ connection }); // no wallet: reads only

const score = await client.getScore(
  new PublicKey("SomeAgentAuthority1111111111111111111111111"),
);
console.log(score); // { completions, disputes, score, lastActivity, decayed }
```

### 4.2 Connect with a wallet (writes)

```ts
import fs from "node:fs";
import os from "node:os";
import path from "node:path";
import { Connection, Keypair } from "@solana/web3.js";
import { TaopSolanaClient } from "@taopp/solana";

const connection = new Connection("http://127.0.0.1:8899", "confirmed");
const wallet = Keypair.fromSecretKey(
  Uint8Array.from(
    JSON.parse(
      fs.readFileSync(path.join(os.homedir(), ".config/solana/id.json"), "utf8"),
    ),
  ),
);

const client = new TaopSolanaClient({ connection, wallet });
```

### 4.3 Register an agent and attest a completion

```ts
await client.registerAgent("ipfs://agent-a-profile");

const { signature, completion, completionId } = await client.attest({
  taskType: "summarization",       // hashed with sha256 when a string is passed
  resultUri: "ipfs://result-0",
  // seq is optional; derived from Agent.completions when omitted
});
console.log(completionId, completion.toBase58(), signature);
```

`taskType` accepts a string (hashed with `hashType`), a `number[]`, or a
`Uint8Array`.

### 4.4 Read the score

```ts
const local = await client.getScore(wallet.publicKey);      // computed client-side
const onChain = await client.getScoreOnChain(wallet.publicKey); // simulated instruction
console.log(local.score, onChain.score, onChain.decayed);
```

Both return `{ completions, disputes, score, lastActivity, decayed }` and must
agree. `getScoreOnChain` simulates the `get_score` instruction and decodes its
return data; it requires a wallet (the simulation fee payer) and throws
`WalletRequired` without one, so read-only clients should use `getScore`. It also
throws if the agent account does not exist yet.

### 4.5 Challenge and resolve

```ts
const challenger = new TaopSolanaClient({
  connection,
  wallet: challengerKeypair,
});

await challenger.challenge({
  completion,                 // PublicKey of the completion to challenge
  evidenceUri: "ipfs://fraud-evidence",
});
// The challenger's SOL bond (Config.challenge_bond_lamports) is now escrowed.

// Only the admin or certifier can call this:
await certifierClient.resolveChallenge({ completion, upheld: true });
```

### 4.6 Capabilities

```ts
const { capability, capabilityId } = await client.registerCapability({
  capabilityType: "LoRA",               // string hashed with sha256
  metadataUri: "ipfs://cap-card",
  bondLamports: 5_000_000,              // 0.005 SOL, must be rent-exempt
});

await certifierClient.certifyCapability(capability);

const results = await client.discover({
  capabilityType: "LoRA",
  minScore: 1,                // default 0
  includeUncertified: false,  // default false
});
// [{ agent, capability, capabilityId, capabilityType, certified, slashed,
//    bondLamports, metadataUri, completions, disputes, score, decayed }, ...]
// sorted by score descending

await certifierClient.slashCapability(capability, 2_000_000); // partial slash
await client.withdrawCapabilityBond(capability);              // creator only
```

### 4.7 Deployment files and helpers

```ts
import {
  loadDeployment,
  clientFromDeployment,
  computeScore,
  hashType,
  createPdas,
} from "@taopp/solana";

const deployment = loadDeployment("./deployments.solana.json");
const client = clientFromDeployment(deployment, { connection, wallet });

computeScore({ completions: 10, disputes: 1, lastActivity: 0, now: 0 });
hashType("LoRA");                 // number[] (32 bytes, sha256)
createPdas(client.programId);     // all PDA derivations
```

Other reads: `getConfig()`, `getAgent(authority)`, `fetchAgents(authorities)`
(batched `getMultipleAccounts`), `getCompletion`, `getChallenge`,
`getCapability`. Admin operations: `initializeConfig`, `updateConfig`,
`setCertifier`.

## 5. MCP walkthrough

The MCP server exposes the reputation loop as tools over stdio, so any
MCP-compatible agent can vet another agent mid-run.

Start it directly:

```sh
TAOP_CHAIN=solana \
SOLANA_RPC_URL=http://127.0.0.1:8899 \
SOLANA_KEYPAIR=~/.config/solana/id.json \
npx tsx packages/mcp-server/src/index.ts
```

- `TAOP_CHAIN` defaults to `solana`; set `TAOP_CHAIN=base` to use the Base
  adapter instead.
- Reads work without a signer; writes (`attest_completion`,
  `challenge_completion`, `register_capability`, `resolve_challenge`) require
  `SOLANA_KEYPAIR` (or `SOLANA_PRIVATE_KEY`, or the `ANCHOR_WALLET` fallback).
- The keypair value may be a JSON keypair file path (with `~` expansion) or a
  base58 secret string.

Use it from the example agent's MCP mode:

```sh
SOLANA_KEYPAIR=~/.config/solana/id.json \
  pnpm --filter @taopp/example-solana-agent start -- --via-mcp --cluster localnet
```

Claude Desktop configuration (`claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "taop-reputation": {
      "command": "npx",
      "args": [
        "tsx",
        "/absolute/path/to/sol-ai/packages/mcp-server/src/index.ts"
      ],
      "env": {
        "TAOP_CHAIN": "solana",
        "SOLANA_RPC_URL": "https://api.devnet.solana.com",
        "SOLANA_KEYPAIR": "/Users/you/.config/solana/id.json"
      }
    }
  }
}
```

Add `SOLANA_PROGRAM_ID` and `SOLANA_DEPLOYMENTS_PATH` if you are not using the
default program id / `deployments.solana.json`. See
`packages/mcp-server/README.md` for the full tool and environment tables.

### Deploying your own

```sh
solana config set --url devnet
solana airdrop 2     # or fund the wallet another way

./scripts/sync-keypair.sh   # copies the committed program-ID keypair into target/deploy/
anchor build
./scripts/sync-idl.sh
anchor deploy --provider.cluster devnet
```

The program id comes from the `[programs.devnet]` entry in `Anchor.toml`
(`8soD4YteLDgkibSNBzmQJTztiNcXPcLoi3Y2FrY15MnE`; the keypair is
`target/deploy/taop_reputation-keypair.json`). Anchor prints the program id and
the upgrade authority (your provider wallet).

Next, initialize the protocol config once and record the deployment. The
canonical way is **`scripts/init-config.ts`** (`pnpm deploy:init`): it reads the
program id from the IDL, calls `initializeConfig` with the
operator-provided certifier/treasury/bond/decay values, and writes
`deployments.solana.json` for the SDK and the MCP server. The equivalent SDK
call is:

```ts
import { Connection, Keypair, PublicKey } from "@solana/web3.js";
import { TaopSolanaClient } from "@taopp/solana";

const connection = new Connection("https://api.devnet.solana.com", "confirmed");
const admin = /* your funded deployer keypair */;
const client = new TaopSolanaClient({ connection, wallet: admin });

await client.initializeConfig({
  certifier: new PublicKey("<CERTIFIER_PUBKEY>"),
  treasury: new PublicKey("<TREASURY_PUBKEY>"),
  challengeBondLamports: 5_000_000,       // 0.005 SOL, >= rent-exempt minimum
  decayPeriodSecs: 2_592_000,             // 30 days
});
```

`initializeConfig` can only ever succeed once per program: the `config` PDA is
created with `init`, so a second call fails. The signer becomes `Config.admin`.

`deployments.solana.json` has this shape (`SolanaDeployment` in
`packages/solana/src/types.ts`):

```json
{
  "cluster": "devnet",
  "programId": "8soD4YteLDgkibSNBzmQJTztiNcXPcLoi3Y2FrY15MnE",
  "config": "<config PDA, base58>",
  "authority": "<admin pubkey, base58>",
  "certifier": "<certifier pubkey, base58>",
  "treasury": "<treasury pubkey, base58>",
  "deployedAt": "2026-01-01T00:00:00.000Z"
}
```

Point tools at it with `SOLANA_DEPLOYMENTS_PATH` (MCP) or `loadDeployment`
(SDK). For mainnet, use
`anchor deploy --provider.cluster mainnet` (see `package.json` for the
`program:deploy:mainnet` script) and rerun the config initialization with
production keys.

## 7. Troubleshooting

### "Detected sbpf_version required by the executable which are not enabled"

A local `solana-test-validator` started from an older feature set refuses to
load a program compiled for newer SBPF features. Start it with the devnet
feature set:

```sh
solana-test-validator \
  --clone-feature-set \
  --url https://api.devnet.solana.com
```

`scripts/localnet.sh` already passes both flags. If you launched your own
validator, restart it with them; do not try to disable the feature set on the
program side.

### Rust tests fail to compile or cannot find the program

- Missing `declare_program!` output: run `./scripts/sync-idl.sh` after
  `anchor build` so `idls/taop_reputation.json`
  exists.
- `include_bytes!` failure or stale behavior: the tests embed
  `target/deploy/taop_reputation.so`; run `anchor build` first and rebuild
  after any program change.
- `cargo test` picks up a different toolchain than `anchor build`: use the
  stable toolchain for both, and keep Anchor at 1.1.2.

### LiteSVM / Anchor version pitfalls

The Rust harness uses `anchor-litesvm 0.4.0` and Anchor `1.1.2` with the
`init-if-needed` feature. Symptoms of a version mismatch:

- Tests panic while deserializing accounts or cannot load the program — the
  `.so` was built by a different Anchor/Solana CLI version. Re-run
  `anchor build` with the pinned toolchain.
- `cargo test` compiles but `declare_program!` references unknown instruction
  or account types — the synced IDL is stale. Re-run `./scripts/sync-idl.sh`.
- LiteSVM does not emulate a validator: there is no `solana-test-validator`
  process involved, so RPC-based flows (the SDK integration tests) still
  require `./scripts/localnet.sh`.

### SDK integration tests are skipped

`packages/solana/test/integration.test.ts` probes the RPC endpoint and skips
the suite when it cannot connect. Start the validator (`./scripts/localnet.sh`)
or point `TAOP_RPC_URL` at a cluster that has the program deployed. The
integration suite also needs a funded wallet at `ANCHOR_WALLET` (default
`~/.config/solana/id.json`).

### MCP server exits or writes fail

- The server speaks stdio, so running it in a terminal shows nothing but the
  startup line on stderr; that is expected. Use an MCP client (or the example's
  `--via-mcp` mode) to call tools.
- Write tools fail with `This write operation requires a signer`: set
  `SOLANA_KEYPAIR` (Solana) or `PRIVATE_KEY` (Base) as described in
  `packages/mcp-server/README.md`.
- The Base adapter requires a deployments file (`DEPLOYMENTS_PATH`, default
  `./deployments.json`); the Solana adapter defaults to devnet and the pinned
  program id, so it works with no configuration for reads.
